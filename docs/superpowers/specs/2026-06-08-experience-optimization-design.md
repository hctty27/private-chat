# 私聊系统体验优化设计

日期：2026-06-08

## 结论

按“分阶段上线”推进全部体验优化：

1. **第一阶段：核心可靠性体验** — 先解决消息发送、断线重连、新消息提示、上传反馈。
2. **第二阶段：移动端顺滑度** — 再处理键盘、表情面板、输入栏、滚动交互。
3. **第三阶段：产品质感和完整度** — 最后优化联系人列表、已读状态、媒体卡片、伪装页、安全提示。

该顺序优先保证聊天工具的可信度，再提升高频移动端操作，最后做视觉和完整度打磨。

## 背景

当前项目是伪装成微博“有趣”的 1 对 1 加密私聊系统。项目已有较完整的聊天基础：联系人列表、桌面/移动端聊天页、WebSocket 重连、消息虚拟列表、历史消息分页、已读检测、文件上传和媒体预览。

近期提交已经围绕 WebSocket、移动端输入、历史消息和聊天交互做过优化。因此本轮不重写架构，而是在现有代码基础上补齐体验状态和边界反馈。

## 设计原则

- 不一次性重写聊天页。
- 不随意引入新依赖。
- 复用现有 Vue、Pinia、WebSocket、虚拟列表和上传能力。
- 优先修复体验根因，而不是只加提示文案。
- 每个阶段独立交付、独立验证。
- 行为变更补充对应测试或可验证用例。
- 只做体验优化相关修改，不做无关重构。

## 第一阶段：核心可靠性体验

### 目标

让用户明确知道消息、网络和上传当前处于什么状态，减少“到底发没发出去”的不确定感。

### 范围

#### 1. 消息发送状态

新增前端消息状态，用于展示：

- `sending`：发送中。
- `sent`：已被服务端确认。
- `failed`：发送失败。
- `queued`：断线期间待发送。

发送文本或表情时，先在当前会话本地插入一条临时消息。WebSocket 可用时立即发送；不可用时进入待发送队列。服务端回推正式消息后，用正式消息替换临时消息，避免重复展示。

为了可靠匹配临时消息和服务端回推，优先考虑在客户端发送消息时附带轻量 `clientMsgId`。如果后端当前协议不支持，则在第一阶段实现时评估两种方案：

1. **推荐方案：扩展 WebSocket chat data 增加 `clientMsgId`**，后端保存/回推时透传，用于前端去重和状态确认。
2. **兼容方案：只在前端用内容、接收者、发送时间窗口做弱匹配**，无需后端改动，但去重可靠性较低。

若实现阶段确认后端改动成本低，采用推荐方案。

#### 2. 发送失败与重试

当消息发送失败或长时间未收到确认时：

- 气泡旁显示失败状态。
- 用户可点击失败状态重试。
- 重试复用原消息内容、类型、接收者和 `clientMsgId`。
- 重试时状态重新变为 `sending` 或 `queued`。

断线期间不直接判定失败，而是显示“待发送”。长时间重连失败后，保留待发送状态并允许用户手动重连。

#### 3. WebSocket 连接状态

复用现有 `wsStatus`，增强界面反馈：

- `connected`：不打扰展示，可用小绿点或短暂“网络已恢复”。
- `reconnecting`：顶部显示“连接已断开，正在重连…”。
- `disconnected`：顶部显示“连接不可用，请检查网络”，并提供“重连”按钮。

重连成功后：

- 短暂显示“网络已恢复”。
- 补拉当前会话消息。
- 刷新待发送队列。
- 避免重复消息。

#### 4. 新消息提示与回到底部

基于现有 `useChatScroll()` 的 `isNearBottom()`：

- 用户接近底部时，新消息自动滚到底部。
- 用户正在看历史消息时，不强制滚动。
- 底部浮出“有新消息”或“回到底部”按钮。
- 点击按钮平滑滚到底部，并清除新消息计数。

这项改动必须保护现有历史消息加载的滚动锚点，避免加载旧消息时位置跳动。

#### 5. 上传反馈和重试

文件上传体验从输入栏进度条升级为更明确的消息级反馈：

- 选择文件后显示文件名、大小和类型提示。
- 上传中显示进度。
- 上传成功后发送正式文件/图片/视频消息。
- 上传失败显示失败状态并支持重试。
- 文件过大继续拦截，但提示从 `alert()` 调整为统一轻提示或页面内提示。

第一阶段先保证上传失败可感知、可重试；媒体卡片样式放到第三阶段。

### 第一阶段涉及模块

- `frontend/src/stores/chat.ts`
- `frontend/src/composables/useChatScroll.ts`
- `frontend/src/views/ChatPage.vue`
- `frontend/src/views/MobileChat.vue`
- `frontend/src/types/index.ts`
- 如采用 `clientMsgId`，还会涉及后端 WebSocket 消息处理与模型/响应透传。

### 第一阶段错误处理

- 消息发送超时：状态置为失败，可重试。
- WebSocket 断开：聊天消息进入待发送队列。
- 重连失败：保留待发送消息，显示手动重连入口。
- 上传失败：显示失败状态，可重新上传。
- 历史消息补拉失败：不清空当前消息，给出重试提示。

### 第一阶段验证

- 在线发送文本、表情、图片、文件。
- 断网后发送消息，恢复网络后自动补发。
- 发送失败后点击重试。
- 重连成功后不出现重复消息。
- 用户看历史消息时，新消息不强制滚到底。
- 点击“回到底部”后位置正确。
- 前端构建通过；如改后端，后端测试/构建通过。

## 第二阶段：移动端顺滑度

### 目标

解决移动端键盘、输入框、表情面板、消息滚动之间互相影响的问题，让手机聊天更稳定。

### 范围

#### 1. 输入框聚焦体验

- 输入框获得焦点时不强制把消息列表异常顶到底。
- 保持用户当前阅读位置，除非用户本来就在底部。
- 发送消息后才滚到底部。

#### 2. 表情面板

- 表情面板打开时，消息区域高度自然收缩。
- 表情面板关闭后恢复布局。
- 点击消息区域时关闭表情面板。
- 表情追加后输入框保持焦点。

#### 3. 键盘适配

- 继续使用 `visualViewport` 处理移动端可视区域变化。
- iOS 和 Android 分别验证。
- 避免输入栏被安全区或键盘遮挡。

#### 4. 输入栏状态

- 长文本输入时 textarea 高度限制保持稳定。
- 发送按钮空内容时弱化，有内容时高亮。
- 文件按钮和表情按钮保留清晰点击反馈。

### 第二阶段涉及模块

- `frontend/src/views/MobileChat.vue`
- `frontend/src/views/ChatPage.vue`
- `frontend/src/composables/useChatScroll.ts`
- `frontend/src/components/EmojiPicker.vue`（如复用/调整表情组件）

### 第二阶段验证

- iOS Safari 或模拟器输入消息。
- Android Chrome 或模拟器输入消息。
- 打开/关闭表情面板。
- 输入长文本。
- 查看历史消息时聚焦输入框。
- 发送后滚动位置正确。

## 第三阶段：产品质感和完整度

### 目标

在核心体验稳定后，提升整体完成度，让应用更像成熟聊天工具，同时保持“伪装微博”的产品特征。

### 范围

#### 1. 联系人列表

- 未读和最近消息排序更自然。
- 搜索命中昵称高亮。
- 联系人为空、搜索为空、加载失败状态更明确。
- 退出登录增加确认，避免误触。
- 在线状态文案可从小绿点扩展为“在线/离线”。

#### 2. 已读状态

- 只在最后一条自己发送的消息显示已读/未读。
- 连续多条自己消息不重复显示状态。
- 对方已读变化时只更新必要区域。

#### 3. 媒体消息

- 图片加载失败显示占位。
- 视频消息使用视频卡片展示。
- 文件消息展示图标、文件名、大小、下载入口。
- 媒体预览保留关闭、加载中、播放控制等反馈。

#### 4. 伪装页

- 伪装页内容更自然，减少固定假数据感。
- 保持入口隐蔽且稳定，不影响用户正常进入。
- 登录态过期或退出后默认回到伪装页。
- 登录页和伪装页视觉风格保持一致。

#### 5. 安全体验

- 收到 `kicked` 消息时，明确提示“账号已在其他设备登录”。
- 清理本地状态后回到伪装页或登录入口。
- token 过期时给出明确提示，不让用户误以为只是网络故障。

- `frontend/src/views/LoginPage.vue`

- `frontend/src/views/MobileChat.vue`
- `frontend/src/stores/user.ts`

### 第三阶段验证

- 联系人搜索、未读排序、空状态。
- 最后一条消息已读/未读展示。
- 图片、视频、文件展示和预览。
- 被踢下线流程。
- token 过期后返回路径。
- 伪装页入口仍可稳定进入。

## 数据流设计

### 消息发送

1. 用户点击发送。
2. 前端创建本地临时消息，状态为 `sending` 或 `queued`。
3. WebSocket 可用时发送 chat 消息；不可用时进入待发送队列。
4. 服务端保存并回推正式消息。
5. 前端通过 `clientMsgId` 或兼容匹配逻辑替换临时消息。
6. 若超时或发送失败，状态置为 `failed`。
7. 用户点击重试后重新进入发送流程。

### 新消息接收

1. WebSocket 收到 chat 消息。
2. 若属于当前会话，加入消息列表或替换临时消息。
3. 若用户接近底部，自动滚到底部。
4. 若用户不在底部，增加新消息计数并显示浮动按钮。
5. 若消息属于其他联系人，更新联系人最近消息和未读数。

### 已读状态

1. 消息进入可见区域后触发已读上报。
2. 后端广播 read 消息。
3. 发送方收到 read 后更新自己消息的已读状态。
4. 前端只在最后一条自己消息上展示状态。

## 测试与验收策略

每个阶段完成后都要单独验证，不把所有优化堆到最后一次验收。

### 自动验证

- 前端构建：`cd frontend && npm run build`
- 后端构建：`cd backend && go build ./cmd/privatechat`
- 后端测试：`cd backend && go test ./...`（如涉及后端）

### 手动验证

- 桌面端聊天。
- 移动端聊天。
- 弱网、断网、重连。
- 历史消息上拉加载。
- 新消息到达时用户不在底部。
- 图片、视频、文件上传。
- 登录过期和被踢下线。

## 非目标

本轮不做以下事情：

- 不新增群聊。
- 不新增朋友圈/微博真实功能。
- 不替换 UI 框架。
- 不重写后端存储模型，除非 `clientMsgId` 去重确认必须轻量扩展。
- 不改变文件存储策略。
- 不做与体验优化无关的重构。

## 风险

1. 本地临时消息和服务端正式消息匹配失败会造成重复消息。
2. 虚拟列表滚动锚点容易受新消息提示影响。
3. 移动端键盘适配存在设备差异。
4. 上传重试需要避免重复发送同一个文件消息。
5. 伪装页如果过度复杂，可能影响真实入口效率。

## 风险控制

- 优先小步提交每个阶段。
- 先做核心路径，再做视觉细节。
- 每个阶段保留明确验证清单。
- 对 WebSocket 协议扩展保持轻量兼容。
- 所有体验失败态优先保留现有数据，不清空用户当前聊天上下文。
